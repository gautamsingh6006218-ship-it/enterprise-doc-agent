# Enterprise Document AI Agent

Production-grade RAG (Retrieval-Augmented Generation) pipeline. Ingest documents from files, Confluence, SharePoint, Jira, or a watched directory. Ask questions in natural language — answers are generated by a local Llama model using retrieved document context.

---

## What It Does

```
Upload PDF / DOCX / TXT / HTML / PPTX / XLSX / ...
         │
         ▼
[1] Ingest       → extract text (PyMuPDF → Docling → OCR fallback)
[2] Preprocess   → clean, normalize, detect language & metadata
[3] Chunk        → 512-token chunks with sentence-window links
[4] Embed        → BGE-M3 dense + sparse vectors → pgvector
         │
         ▼
Ask a question
         │
         ▼
[5] Encode query → BGE-M3 1024-dim vector
[6] Retrieve     → dense + BM25 keyword search → RRF fusion → reranker
[7] Answer       → Llama 3.2 (via Ollama, runs locally)
```

## Setup — Step by Step

### Step 1 — Clone and create virtual environment

```bash
git clone <repo-url>
cd Enterprise-doc-agent

python3 -m venv .venv
source .venv/bin/activate          # macOS / Linux
# .venv\Scripts\activate           # Windows
```

> **Note (macOS with Anaconda):** If `which python` still shows Anaconda after activating,  
> use `.venv/bin/python` directly instead of `python` for all commands below.

---

### Step 2 — Install Python dependencies

```bash
pip install -r requirements.txt

# transformers must be pinned below 5.0 (FlagEmbedding reranker compatibility)
pip install "transformers>=4.47,<5.0"
```

---

### Step 3 — Start PostgreSQL + pgvector (Docker)

```bash
docker compose up -d
```

This starts a PostgreSQL 16 container with the pgvector extension and automatically creates the `document_chunks` and `documents` tables.

Verify it is healthy:

```bash
docker compose ps
# enterprise_doc_db should show "healthy"
```

---

### Step 4 — Pull the Llama model (Ollama)

Make sure Ollama is running, then pull the model:

```bash
ollama pull llama3.2
```

This downloads ~2 GB. Run once, reused on every startup.

## Using the App

### Chat (ask questions)

1. Go to the **Chat** tab
2. Type any question about your documents
3. The answer is generated by Llama 3.2 using the most relevant document chunks
4. Click **"N sources"** below an answer to see exactly which document chunks were used

### Documents (upload & manage)

1. Go to the **Documents** tab
2. Drag and drop files onto the upload zone — or click **Browse**
3. Supported formats: PDF, DOCX, PPTX, XLSX, CSV, TXT, MD, HTML, EML, PNG, JPG, JPEG, TIFF
4. Click **Upload** — each file is processed through the full pipeline
5. Status badges:
   - `completed` — indexed and searchable
   - `duplicate` — identical file already ingested, skipped
   - `failed_*` — pipeline error (hover for details)
6. Click the trash icon to delete a document (also removes its vectors from pgvector)

### Re-uploading a changed document

If you upload a file with the **same name** but **different content**, the system automatically deletes the old version and indexes the new one. No manual deletion needed.

## API Reference

All endpoints require `Authorization: Bearer <token>`.

| Method | Endpoint | Description |
|---|---|---|
| `POST` | `/api/ingest` | Upload a single file |
| `POST` | `/api/ingest/batch` | Upload multiple files at once |

```bash

  -F "visibility=public"
```

## Auto-Sync Features

### Watch a local folder

Set `WATCH_DIR` in `.env` to a folder path. Any file dropped into that folder is automatically ingested. Changed files are automatically re-ingested (old version replaced).

```env
WATCH_DIR=/Users/you/Documents/company-docs
WATCH_TENANT_ID=acme
WATCH_RECURSIVE=true
```

### Scheduled connector sync

Set `SYNC_SOURCES` and `SYNC_INTERVAL_MINUTES` in `.env`. The server polls each connector on a background schedule and ingests new/updated documents.

```env
SYNC_SOURCES=confluence,jira
SYNC_INTERVAL_MINUTES=60
SYNC_TENANT_ID=acme
```

## Module Boundaries

The app is a modular monolith: one process, one database, and two top-level packages.

- `agent/` holds the RAG modules, one module per package. Each module exports its public API from its `__init__.py`. Other code imports only from there (`from agent.registry import RegistryService`), never from internal paths (`agent.registry.store`).
- `backend/` holds only backend logic: HTTP routes, auth, request/response schemas, service wiring, and the scheduler and file-watcher jobs. A route or job checks its input, calls one RAG service, and maps the result. All RAG logic — dedup, parsing, chunking, embedding, retrieval, answer generation — lives in `agent/`. The backend may import any RAG module's public API, but it never imports an ML, parsing or vector library itself. Nothing in `agent/` imports `backend/`.

Each RAG module may import only these modules:

```
sync ────────► connectors, pipeline, registry
documents ───► embeddings, registry, pipeline
pipeline ────► ingestion, processing, chunking, embeddings, registry
qa ──────────► shared, retrieval, llm
retrieval ───► shared, embeddings
llm ─────────► shared
embeddings ──► shared, ingestion
chunking ────► ingestion, processing
processing ──► ingestion
ingestion, registry, connectors, shared ──► nothing
```

Each table has one owner: `registry` owns `documents`, `embeddings` owns `document_chunks`. Only `documents.DocumentService` changes both.

`tests/architecture/test_module_boundaries.py` enforces these rules, including the list of RAG libraries that `backend/` may not import (`RAG_LIBRARIES`). To add a module, create `agent/<name>/__init__.py` with its exports, then add `<name>` and its dependencies to `MODULE_DEPENDENCIES` in that test.

## Architecture Decisions

| Decision | Reason |
|---|---|
| PostgreSQL + pgvector (not Qdrant/Pinecone) | Vectors and RBAC metadata in one DB — no dual-write problem |
| BGE-M3 (not separate dense + BM25 models) | One model produces both — no second service to manage |
| bge-reranker-v2-m3 local (not Cohere Rerank API) | Enterprise documents must not leave the organisation |
| Llama 3.2 via Ollama (not OpenAI/Anthropic) | Fully local — no data sent to external APIs |
| Result pattern everywhere (never raises) | All services return `XxxResult(success, data, error)` — safe in async workers |
| RBAC enforced in SQL (not post-filter) | Guarantees exactly top_k RBAC-valid results, not top_k minus filtered |
